# NotVerify — Strategic Architecture Reference

> Comprehensive technical documentation for the Straker.AI Adaptive Command Surface prototype.
> For the point-in-time technical audit (issue inventory, codebase metrics), see [architecture-audit.md](./architecture-audit.md).

**Last updated:** 2026-03-31
**Codebase:** ~36K lines across 100 source files (JSX/JS)
**Status:** Clickable frontend prototype — simulation only, no backend

---

## Purpose

NotVerify is a **clickable frontend prototype** for an AI-powered enterprise localization quality assurance platform, branded "Straker.AI — Adaptive Command Surface." It demonstrates a vision where enterprise localization admins interact with a predictive co-pilot that recommends projects, assembles AI agent ensembles, performs document analysis, runs simulated translation pipelines, and delivers explainable quality narratives — all without a single real API call. The entire experience is deterministic client-side theatre designed to sell a product concept to stakeholders and investors.

The target persona is a localization program manager at a mid-to-large enterprise (the prototype uses "Meridian Capital" as the demo org) managing multi-locale document translation across financial, legal, and marketing verticals with regulatory compliance requirements (J-GAAP, IFRS, TSE).

## Architecture Overview

The application is a **single-page React 19 app** with no routing library, no state management library, and no backend. All state lives in `App.jsx` via `useState` hooks. Navigation is a `phase` string variable that selects which component tree renders. Data is generated by deterministic factory functions.

## Core Components

### 1. App.jsx — The God Component

- **What it does:** Central state machine holding all application state, all phase routing logic, all callback handlers, and ~200 lines of inline data generator functions.
- **Key file:** `src/App.jsx` (1,032 lines)
- **State inventory:** ~25 `useState` variables covering phase navigation, file data, structured context, triage results, upsell selections, agent management, campaign state, review mode, and UI overlay toggles.
- **Connection pattern:** Every child component receives its props directly from App.jsx. Callbacks like `handleFileAccepted`, `handleReadingComplete`, `handleProcessingComplete`, and `handleReset` drive all phase transitions.
- **Notable patterns:**
  - Phase routing via conditional rendering (`{phase === 'dashboard' && <CommandSurface ... />}`)
  - Safety net `useEffect` that redirects to dashboard if data-dependent phases have no data
  - Overlay components (`IntelligenceMarketplace`, `CustomAgentStudio`, `AgentProfile`, etc.) rendered unconditionally with `isOpen` props
  - Debug hooks exposed on `window` (`__setPhase`, `__setShowMarketplace`, `__setHumanReviewMode`) without `import.meta.env.DEV` guards

## Data Flow

### Single-Document Flow

```
User uploads file (or selects predicted project)
    │
    ▼
App.jsx: handleFileAccepted(file)
    ├── Generates triageData via inline functions:
    │   getClassification(file)     → "47-page PDF, English Earnings Report"
    │   getIntent(file, context)    → "Japanese Financial Processing (J-GAAP)"
    │   getAgent(file, context)     → { name: 'JP-FIN-3', id: 'JP-FIN-3' }
    │   getPlan(file, context)      → { guardrails: [...] }
    │   getSourceIQ(file, context)  → { overall: 73, dimensions: [...] }
    │   getQualityScore(file, ctx)  → { overall: 76, potential: 89, dimensions: [...] }
    │   getUpsellOptions(file, ctx) → [{ id: 'glossary', impact: [...] }, ...]
    │   getSandboxPreview(file, ctx)→ { segments: [...], stats: {...} }
    │
    ├── Generates discoveryFindings via generateDiscoveryStream(file, context)
    │   → Array of { delay, category, text, severity, scanLabel }
    │
    ├── Sets triageData, discoveryFindings state
    └── Sets phase → 'reading'
         │
         ▼
    MissionControl — Receives triageData, discoveryFindings
    Shows analysis pipeline, agent configuration, quality projection
    User clicks "Deploy" → handleReadingComplete(deployConfig)
         │
         ▼
    App.jsx: Sets activeAgents, sets phase → 'processing'
         │
         ▼
    LiveTelemetry — Receives agents, locales, duration
    Runs scripted animation (12-15s), progress simulation
    Calls onComplete(completedJobs)
         │
         ▼
    App.jsx: handleProcessingComplete → sets phase → 'narrative'
         │
         ▼
    QualityNarrative — Receives triageData, computedQuality, qualityNarrative
    computedQuality = useQualityCalculator(baseScore, upsells, enabledUpsells)
    qualityNarrative = generateQualityNarrative(triageData, enabledUpsells, orgIntelligence)
         │
         ▼
    User clicks "Start New" → handleReset()
    Clears all state, increments projectsCompleted
    First completion → 'time-jump' phase (cinematic fast-forward)
    Subsequent → 'dashboard' phase
```

### Campaign (Batch) Flow

```
User navigates to CampaignHub
    │
    ▼
CampaignHub: Step 1 — Upload files, configure campaign

    Document type auto-detected by filename heuristics
    Ensemble auto-recommended per document type
    │
    ▼

    Shows document × locale matrix
    Ensemble mismatch warnings via checkEnsembleMismatch()

    │
    ▼
App.jsx: Sets activeCampaign, sets phase → 'processing'
    │
    ▼
OperationsControlRoom — Receives campaign
    Builds job list: documents × locales → flat job array
    Runs simulated progress intervals with random quality scores (72-98)
    Calls onComplete(completedJobs)
    │
    ▼
App.jsx: handleProcessingComplete → updates campaign docs with results
    Sets phase → 'narrative'
    │
    ▼
CampaignResultsView — Receives campaign with populated localeResults
    Shows document × locale result grid with quality scores
    "Review" button → handleCampaignReviewJob(job) → human-review phase
```

### Data Generator Architecture

All data is **deterministic** — the same file name + structured context always produces the same mock data. There are two generator tiers:

**Tier 1: External generators (`src/data/`)**
| File | Function | Output |
|------|----------|--------|
| `campaignModel.js` | `createCampaign()`, `createDocumentRecord()`, `detectDocumentType()` | Campaign/document objects with typing |
| `discoveryFindings.js` | `generateDiscoveryStream(file, context)` | Timed finding stream (delay-based animation data) |
| `orgIntelligence.js` | `generateOrgIntelligence()` | Static org profile (projects, locale stats, predictions) |
| `qualityNarrative.js` | `generateQualityNarrative(triage, upsells, org)` | Before/after scores, org improvements, cumulative intelligence |
| `localeConstellation.js` | `localeConstellationData` | Static locale metadata (23 locales with complexity, family, flags) |

**Tier 2: Inline generators (`App.jsx` lines 800-1032)**
8 functions (`getClassification`, `getIntent`, `getAgent`, `getPlan`, `getSourceIQ`, `getQualityScore`, `getUpsellOptions`, `getSandboxPreview`) that branch on file extension and primary locale to produce mock triage data. These should be extracted to `src/data/` for consistency.

## Patterns & Conventions

### Animation Pattern

Framer Motion is imported in 59 of 100 source files — it's the backbone of the UI feel. The standard pattern is:

```jsx
const SPRING = { type: 'spring', stiffness: 300, damping: 20 }

<AnimatePresence>
  {visible && (
    <motion.div
      initial={{ opacity: 0, y: 8 }}
      animate={{ opacity: 1, y: 0 }}
      exit={{ opacity: 0, y: 8 }}
      transition={SPRING}
    >
      ...
    </motion.div>
  )}
</AnimatePresence>
```

Every major component defines its own `SPRING` constant. The `useReducedMotion()` hook gates animations for users who prefer reduced motion, and a CSS fallback enforces `animation-duration: 0.01ms` as a hard stop.

### Portal Pattern

Full-page overlays and modals use `createPortal` to render outside the main DOM tree: `IntelligenceMarketplace`, `IntelligenceAssistant`, `TeamDirectory`, `AgentDetailView`, `Modal`, `Drawer`, `ConcordanceOverlay`, `CreditsAndBilling` (3 modals). Portal components universally lock body scroll, attach Escape key listeners, and use `useFocusTrap` for accessibility.

### Mock Data Pattern

Data generators are **branch-on-locale-and-extension** functions that return hardcoded objects. The pattern:

```javascript
function getIntent(file, structuredContext) {
  if (primaryLocale(sc) === 'ja') return 'Japanese Financial Processing (J-GAAP Compliance)'
  if (primaryLocale(sc) === 'de') return 'EU Regulatory Processing (IFRS Compliance)'
  // ... more branches
  return 'Document Processing & Compliance Review'  // fallback
}
```

This creates a demo that feels data-driven but is actually a decision tree. It's effective for prototyping but will need complete replacement with real API calls.

### Component Composition Pattern

Large page components compose visualization sub-components rather than rendering everything inline. Example from `QualityNarrative.jsx`:

```
QualityNarrative
  ├── ValueCreationEngine (ROI metrics)
  ├── AnomalyTrendChart (SVG line chart)
  ├── IntelligenceTriage (issue prioritization)
  ├── QualityHeatmap (document × locale grid)
  └── CampaignExportWizard (export format selector)
```

This pattern is good but applied inconsistently — `HumanReview.jsx` (2,027 lines) and `CustomAgentStudio.jsx` (1,417 lines) contain everything inline rather than composing sub-components.

### Accessibility Pattern

Consistent attention to accessibility throughout:

- Skip-to-content links on every page layout
- 129 `aria-*` attributes across the codebase
- `role="banner"`, `role="menu"`, `role="listitem"`, `aria-expanded`, `aria-haspopup` on interactive elements
- `useFocusTrap` applied to all portal-rendered overlays
- `useReducedMotion` checked in every animated component
- Keyboard event handlers (`Escape` to close, `Tab` trapping) on modals/drawers
- `prefers-reduced-motion` CSS fallback in `index.css`

## Strategic Assessment

### Strengths

1. **Product vision is exceptional.** The prototype demonstrates a compelling, differentiated enterprise localization product. The predictive co-pilot, explainable quality narratives, agent marketplace, and Cortex concepts are genuinely novel for this space.

2. **UI/UX polish is high.** Framer Motion animations are smooth and purposeful. The design system is consistent — a single blue brand scale with clear semantic color tokens. Typography hierarchy is clean. The "Security Theatre" processing visualization is exactly the kind of trust-building theatre enterprise buyers need.

3. **Accessibility is ahead of most prototypes.** Focus traps, reduced motion support (both JS and CSS), skip links, ARIA attributes, and keyboard navigation are present and functional. This isn't common in prototype-stage code.

4. **Data generators are well-architected for their purpose.** The deterministic factory pattern (`campaignModel.js`) with JSDoc typedefs, config inheritance (campaign → document), and ensemble recommendation heuristics shows thoughtful domain modeling. The campaign data model (`Campaign → Documents → LocaleResults`) is a solid foundation for the real data layer.

5. **Composable visualization components.** `QualityNarrative` composing `ValueCreationEngine`, `AnomalyTrendChart`, `IntelligenceTriage`, and `QualityHeatmap` as independent sub-components is the right pattern and will scale well.

### Risks & Tech Debt

#### 🔴 Critical

- **App.jsx god component (1,032 lines, 25+ state vars).** This is the load-bearing wall of the entire application. Every new feature adds more state, more callbacks, and more conditional rendering branches here. Refactoring this into a proper state machine (XState), a router (React Router/TanStack), and domain-specific context providers is **prerequisite** to production development. Estimated effort: 2-3 weeks of focused refactoring.

- **No error boundaries anywhere.** A runtime crash in any of the 84 components unmounts the entire application. For a prototype shown in demos, this means one bad state transition kills the presentation. Add `<ErrorBoundary>` wrappers at minimum around each phase component.

- **GDPR violation via Google Fonts CDN** (`index.html:8-10`). Every page load sends user IP addresses to Google. For EU-based enterprise customers, this is a compliance blocker. Fix: self-host Inter and JetBrains Mono woff2 files in `public/fonts/`.

#### 🟡 Important

- **6 files exceed 1,000 lines.** `HumanReview.jsx` (2,027), `CustomAgentStudio.jsx` (1,417), `QualityNarrative.jsx` (1,356), `CommandSurface.jsx` (1,137), `CreditsAndBilling.jsx` (1,062), `OrgBrain.jsx` (1,038). These monoliths are hard to modify without introducing regressions. `HumanReview.jsx` in particular should be decomposed into 5-8 sub-components (segment editor, toolbar, sidebar, filter panel, etc.).

- **Debug hooks on `window` (App.jsx:46, 61, 74).** `window.__setPhase`, `window.__setShowMarketplace`, and `window.__setHumanReviewMode` are exposed in all environments. Anyone can open the console and `__setPhase('narrative')` to skip to any screen. Gate behind `import.meta.env.DEV`.

- **8 `console.log` statements in production code.** Five in `App.jsx` callback handlers, three in components. These will leak internal state names in production browser consoles.

- **No TypeScript.** With 100 files, ~25 state variables, 20+ callback signatures, and complex prop shapes (triageData, qualityNarrative, campaign objects), the lack of type safety means errors are only caught at runtime. TypeScript migration would be high-impact but also high-effort at this stage.

- **Duplicated locale data.** Locale lists (`ALL_LOCALES`, `LOCALES`, `LANGUAGES`, `LOCALE_META`) are defined independently in `CommandSurface.jsx`, `OnboardingFlow.jsx`, `LiveTelemetry.jsx`, and `localeConstellation.js`. A single canonical locale registry should be the source of truth.

- **`localStorage` used for state that belongs on a server.** Knowledge rules, propagation settings, and review state are persisted in `localStorage` with no encryption, expiry, or size management. In multi-tenant production, this data must be server-side.

#### 🟢 Minor

- **Package name mismatch.** `package.json` calls the project `"product-x"`, not `"not-verify"` or `"straker-ai"`.
- **Default agent data duplicated.** `DEFAULT_AGENTS` is defined independently in `App.jsx`, `MissionControl.jsx`, and `LiveTelemetry.jsx` with slightly different shapes.
- **`SPRING` constant defined 15+ times.** Every file defines `const SPRING = { type: 'spring', stiffness: 300, damping: 20 }` independently. Should be a shared constant.

### Missing Pieces

For a **prototype**, what's here is appropriate. For a path to **production**, these are required:

| Category | What's Missing | Priority |
|----------|---------------|----------|
| **Backend** | No server, no API, no database, no real processing | P0 — nothing works without this |
| **Authentication** | No login, sessions, tokens, RBAC | P0 — enterprise requirement |
| **Routing** | No URL-based navigation, deep links, code splitting | P1 — UX and performance |
| **State management** | No reducer, no context tree, no state machine | P1 — prerequisite for multi-feature dev |
| **Type system** | No TypeScript | P1 — blocks safe refactoring |
| **Testing** | Zero tests of any kind | P1 — blocks safe refactoring |
| **Error handling** | No error boundaries, no error states in components | P1 — runtime resilience |
| **CI/CD** | No GitHub Actions, no Docker, no deployment pipeline | P2 — blocks team velocity |
| **Monitoring** | No Sentry, no analytics, no performance tracking | P2 — invisible production issues |
| **i18n** | The localization platform itself is not internationalized | P3 — ironic but low priority |

### Scaling Concerns

This question is less relevant for a pure frontend prototype, but considering the path to production:

| Growth Factor | What Breaks |
|---------------|------------|
| **2× features** | `App.jsx` becomes unmanageable. Every new phase adds state, callbacks, and conditional rendering. The file will cross 2,000 lines. Props drilling depth grows. |
| **5× components** | Without a router and code splitting, the initial bundle includes all 84 components. Load time degrades. Without TypeScript, refactoring any shared interface is unsafe. |
| **Real API calls** | Every data generator must be replaced with async fetchers. None of the current components handle loading states, error states, or stale data. No suspense boundaries exist. |
| **Multi-tenant** | `localStorage` state conflicts between users/orgs. No auth means no data isolation. No RBAC means no role-based view gating. |
| **Multiple developers** | Without tests, TypeScript, or a state management pattern, parallel development on the same codebase will produce constant merge conflicts in `App.jsx` and subtle state bugs. |

### Recommended Next Steps

Ordered by impact, assuming the goal is to move this prototype toward a real product:

1. **Self-host Google Fonts** — 30-minute fix, eliminates GDPR risk. Download woff2 files to `public/fonts/`, update `index.html` with `@font-face` rules.

2. **Add error boundaries** — 1-2 hours. Wrap each phase component and each overlay in a `<ErrorBoundary>` that renders a fallback UI instead of crashing the app.

3. **Gate debug hooks behind `import.meta.env.DEV`** — 5-minute fix. Prevents external state manipulation in production builds.

4. **Extract inline generators from App.jsx to `src/data/`** — Half-day. Move `getClassification`, `getIntent`, `getAgent`, `getPlan`, `getSourceIQ`, `getQualityScore`, `getUpsellOptions`, `getSandboxPreview` to `src/data/triageGenerator.js`. Reduces App.jsx by ~200 lines.

5. **Introduce React Router** — 1-2 days. Replace phase string with URL-based routing. Enables deep linking, back/forward navigation, and code splitting with `React.lazy`.

6. **Decompose App.jsx state** — 1 week. Extract domain state into context providers (`ProjectContext`, `AgentContext`, `CampaignContext`, `UIContext`) or adopt Zustand. Eliminate props drilling.

7. **Add TypeScript** — 1-2 weeks incremental. Start with `src/data/` types (Campaign, Document, TriageData), then hooks, then components. Use `allowJs: true` for gradual migration.

8. **Add Vitest + basic tests** — 1 week. Start with data generators (pure functions, easy to test), then hooks, then critical path smoke tests.

9. **Decompose monolith components** — 1-2 weeks. Priority targets: `HumanReview.jsx` (→ 5-8 sub-components), `CustomAgentStudio.jsx` (→ step components), `CommandSurface.jsx` (→ extract panels).

10. **Define API contract** — Before writing backend code, define the API surface that would replace each data generator. The `Campaign → Document → LocaleResult` model in `campaignModel.js` is a solid starting point for the schema.
